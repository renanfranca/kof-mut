## Design and recovery boundaries

Installed entry resolves a concrete release and holds a shared execution lease. Update uses a separate management lease; uninstall attempts both management and exclusive execution access before removal. Execution locks are created during installation and opened for reading during invocation. Missing coordination metadata is an explicit failure, avoiding replacement of an inode held by another process.

The image includes compiled application/generated runtime, VERSION, public docs, LICENSE, NOTICE and receipts. It references external canonical Kof/Java/jar paths and records Kof/JVM versions plus content hashes. Bash verifies bootstrap integrity before starting the JVM; preparation, identity, inventory, activation, management and mutation behavior remain in Kof.

Scoped refactor-design review read its full rubric after green public journeys. No action was justified: invocation properties are process scoped, mutable receipt lists remain inside one management transaction, and repeated validation crosses persistence and JVM launch boundaries. No additional architectural layers were introduced.

Earlier releases are retained. Corrupt payload repair selects a new image and repeated repair reuses the healthy result. Unknown occupied release paths receive a fresh identifier without ownership claims. Uninstall preserves unknown or modified files and persistent coordination/logs. Abrupt termination can leave unactivated or unregistered artifacts; names alone never authorize executing or deleting them. Invalid ownership/coordination metadata and foreign commands require preserving the existing prefix and using a fresh prefix for automatic installation.
